#+title: Tek9

* Tek9DB

Tek9 is a local embedded document and graph database implemented in Common Lisp on top of LMDB.

Version 0.2 keeps the small Lisp-facing API, but moves the storage engine toward LMDB-native data structures instead of rebuilding database machinery in Lisp:

- one LMDB environment per Tek9 database;
- cached named database handles;
- one transaction for bulk mutation;
- ordered primary-key range scans;
- durable secondary indexes using LMDB named databases;
- DUPSORT indexes for one-to-many values;
- sequential APPEND/APPEND-DUP index builders for fast initial loads;
- constant shared graph keyspaces with compact edge IDs and predicate adjacency indexes;
- full durability by default with explicit weaker profiles for rebuildable data;
- environment and database statistics for profiling.

Tek9 is still alpha software. Treat the on-disk format and public API as evolving until a stable release is cut.

** Install

Clone into Quicklisp local projects:

#+begin_src shell
git clone https://github.com/lost-rob0t/tek9.git ~/quicklisp/local-projects/tek9
#+end_src

Then:

#+begin_src lisp
(ql:quickload :tek9)
(use-package :tek9)
#+end_src

** Open a database

The default LMDB map reserves 16 GiB of virtual address space and supports 64 named databases. The map is a capacity ceiling, not a preallocated 16 GiB data file.

#+begin_src lisp
(defparameter *db*
  (open-database
   (new-database "quasar"
                 :path #P"/tmp/quasar-tek9/"
                 :max-size (* 64 1024 1024 1024))))
#+end_src

Keep the environment open for the lifetime of the application instead of reopening it for every operation.

** Durability profiles

=:full= is the default and should be used for canonical user data.

#+begin_src lisp
(new-database "canonical" :path #P"/tmp/canonical/" :durability :full)
#+end_src

=:metadata-lazy= can lose the newest committed transaction after a machine crash but keeps LMDB's transactional structure. =:nosync= skips normal commit flushing and is intended only for disposable or reproducible stores where the caller explicitly accepts the crash-loss tradeoff.

Do not turn sync off just to make a benchmark look good.

** Documents

#+begin_src lisp
(put *db* (new-document :id "person:1"
                        :value '(:dtype "person" :name "Ada")))

(fetch* *db* "person:1")
#+end_src

*** Bulk ingest

Bulk writes share one LMDB write transaction instead of opening and committing one transaction per document.

#+begin_src lisp
(put-bulk *db*
          (loop for i below 100000
                collect (new-document
                         :id (format nil "~12,'0d" i)
                         :value (list :n i))))
#+end_src

If the ids are already in LMDB key order, pass =:sorted t=. Tek9 checks the database's current final key and uses LMDB's append fast path only when it is safe; otherwise it automatically falls back to normal insertion.

#+begin_src lisp
(put-bulk *db* sorted-documents :sorted t)
#+end_src

Large imports do not populate Tek9's materialized-view change vector by default. Use =:track-changes t= only when the caller intends to feed those ids through the legacy incremental view API.

*** Fast indexed initial load

When a source database is empty and its secondary indexes are already registered, =bulk-load= is the fastest intended ingest path. It sorts the documents and extracted index pairs in memory, then append-loads the source B+tree and every index in one LMDB write transaction.

#+begin_src lisp
(register-index
 *db*
 "dtype"
 (lambda (document)
   (getf (doc-value document) :dtype)))

(bulk-load *db* documents)
#+end_src

The source database must be empty. The source rows and every registered index commit atomically. If a unique index rejects a duplicate key, the whole load rolls back.

This path deliberately trades RAM for fewer B+tree comparisons and more sequential page work. Use normal =put-bulk= for incremental ingest.

*** Bulk reads

#+begin_src lisp
(fetch-bulk *db* '("000000000001" "000000000002" "000000000003"))
#+end_src

The ids are resolved inside one read snapshot with one reusable cursor.

** Secondary indexes

A secondary index is another LMDB named database, not a Lisp hash-table cache. Non-unique indexes use DUPSORT so one indexed value maps directly to multiple sorted document ids.

#+begin_src lisp
(register-index
 *db*
 "dtype"
 (lambda (document)
   (getf (doc-value document) :dtype)))

(rebuild-index *db* "dtype")

(index-document-ids *db* "dtype" "person")
(select-index *db* "dtype" "person")
#+end_src

Indexes are maintained in the same write transaction as document replacement and deletion.

For an existing corpus, =rebuild-index= is the bounded-memory path. =rebuild-index-fast= materializes and sorts all index pairs in RAM, then feeds the empty index with LMDB's sequential append flags.

#+begin_src lisp
(rebuild-index-fast *db* "dtype")
#+end_src

Use the fast rebuild when its extracted index pairs comfortably fit in memory; use the streaming rebuild for very large corpora.

Integer indexes can use LMDB's native unsigned-64 ordering:

#+begin_src lisp
(register-index
 *db*
 "created"
 (lambda (document)
   (getf (doc-value document) :created))
 :key-type :uint64)
#+end_src

** Ordered range scans

Primary keys are already ordered by LMDB. Tek9 can seek once and walk sequentially:

#+begin_src lisp
(select-primary-range *db* "person:1000" :end "person:1999")
#+end_src

Secondary indexes support the same pattern:

#+begin_src lisp
(select-index-range *db* "created" 1700000000 :end 1800000000)
#+end_src

Use an index or ordered range when the predicate is indexable. =select= remains the full-scan fallback for arbitrary Lisp predicates.

** Graph storage

Logical graphs do not each consume their own collection of LMDB named databases. Every graph shares a constant physical set of keyspaces, with the logical graph name encoded into each storage key:

#+begin_example
graph/nodes           (graph-name,node-id) -> encoded node
graph/edges           (graph-name,edge-id) -> encoded edge
graph/out             (graph-name,source-node-id) -> DUPSORT edge ids
graph/in              (graph-name,target-node-id) -> DUPSORT edge ids
graph/out-predicate   (graph-name,source-node-id,predicate) -> DUPSORT edge ids
graph/in-predicate    (graph-name,target-node-id,predicate) -> DUPSORT edge ids
#+end_example

Edges have independent compact IDs. This keeps DUPSORT adjacency values small, permits multiple parallel edges between the same two nodes, and avoids rewriting a node whenever an edge changes.

#+begin_src lisp
(defparameter *a* (make-instance 'node :id "a" :props '(:name "A")))
(defparameter *b* (make-instance 'node :id "b" :props '(:name "B")))

(put-nodes *db* (list *a* *b*) :database-name "investigation")

(put-edge *db*
          (make-instance 'edge
                         :source "a"
                         :predicate "knows"
                         :target "b")
          :database-name "investigation")

(fetch-node-neighbors *db*
                      "a"
                      :database-name "investigation"
                      :predicate "knows")
#+end_src

When a predicate is supplied, Tek9 reads the predicate-specific adjacency B+tree instead of loading and filtering every incident edge. Edge records and all generic/predicate adjacency entries are mutated atomically in one LMDB transaction. Neighbor reads resolve adjacency, edge records, and target nodes in one read snapshot.

** Views

Views remain available for derived materialized results. Version 0.2 fixes their transaction boundaries and rebuild path; secondary indexes should be preferred for ordinary equality and range lookup because they avoid running arbitrary map functions across the full corpus.

** Performance rules

1. Keep one LMDB environment open per application database.
2. Batch writes into one transaction whenever the operation is logically atomic.
3. Feed sorted initial or tail-appending loads through =:sorted t=; Tek9 verifies the append precondition before using the fast path.
4. Use =bulk-load= for an empty indexed database when the index-pair working set fits in RAM.
5. Put selective query predicates behind secondary indexes instead of repeatedly decoding every document.
6. Use range cursors for ordered predicates.
7. Use predicate-specific graph adjacency when the relationship type is known.
8. Store graph adjacency in shared DUPSORT keyspaces instead of embedding growing edge lists in node values or creating DBIs per logical graph.
9. Choose a generous LMDB map size up front; it reserves address space rather than eagerly allocating the whole file.
10. Benchmark with the durability profile that production will actually use.
11. Measure environment/database statistics before inventing caches above the memory-mapped store.

Tek9 intentionally does not add its own buffer pool, write-ahead log, or page cache above LMDB. LMDB already owns those storage-engine responsibilities; Tek9 concentrates on key layout, indexing, batching, query planning, graph semantics, and the Common Lisp API.

** Benchmark harness

Load =bench/compare.lisp= after Tek9 and run:

#+begin_src lisp
(tek9-bench-compare:run)
#+end_src

The comparative harness runs with =:full= durability and measures per-document commits versus batching, arbitrary point reads, decoded scans versus secondary indexes, streaming versus sequential index rebuild, and row-maintained versus bulk-built indexed initial ingest. Treat benchmark numbers as machine-specific and compare changes on the same host and dataset.
